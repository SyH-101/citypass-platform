# 项目全景与代码地图

## 业务模块

| 模块 | 入口 | 关键存储/技术 | 面试价值 |
|---|---|---|---|
| 登录 | `UserController` | Redis Hash、滑动续期、ThreadLocal | token 会话与拦截器顺序 |
| 商铺 | `ShopController` | OpenResty、Caffeine、Redis、MySQL | 多级缓存与一致性 |
| 秒杀 | `VoucherOrderController` | Lua、RocketMQ、Redisson、MySQL | 高并发、一致性、幂等 |
| 博客/关注 | `BlogController`、`FollowController` | ZSet、Set、推模式 Feed | Redis 数据结构选型 |
| 签到 | `UserController.sign` | Bitmap/BitField | 位图节省空间 |

## 秒杀类的职责

| 类/文件 | 只负责什么 |
|---|---|
| `VoucherOrderServiceImpl` | 编排 Redis、MQ、锁和结果状态 |
| `VoucherOrderTransactionalService` | 定义订单数据库事务边界 |
| `SeckillTransactionListener` | 决定事务消息提交、回滚或回查 |
| `OrderMQConsumer` | 消费 CREATE/TIMEOUT 并触发幂等业务 |
| `ReliableTaskRepository` | 将外部动作记录进数据库事务 |
| `ReliableTaskScheduler` | 重试延迟消息、库存初始化和 Redis 补偿 |
| `SeckillReconcileTask` | 扫描长尾差异并让库存收敛 |
| `seckill.lua` | A 模式原子资格判断与预扣 |
| `seckill-claim.lua` | B 模式消费者原子 claim |
| `seckill-rollback.lua` | 只回滚当前 orderId 拥有的 claim |

## A 与 B 的区别

| 维度 | A：入口预扣 + 事务消息 | B：先入队 + 消费者 claim |
|---|---|---|
| 入口 Redis 压力 | 有热点 key 访问 | 较低 |
| 用户即时反馈 | 可立即知道库存/重复 | 只能先得到 WAITING |
| 削峰位置 | 网关 + MQ | 网关 + MQ，校验也被削峰 |
| 消息类型 | RocketMQ 事务消息 | 普通消息 |
| 复杂度 | 事务回查更复杂 | 排队状态与消费补偿更复杂 |

面试时不要说 B 一定更好。它牺牲即时反馈，把资格判断推迟到消费者，适合更强的削峰诉求；A 的交互更直接。

## 读写链路分离的准确说法

本项目的“读写分离”指业务链路隔离：商铺读取走缓存链，秒杀写入走限流、MQ 和订单事务。项目没有配置 MySQL 主从数据源，所以不能在简历上写“实现数据库主从读写分离”。
