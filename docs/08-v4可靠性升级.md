# v4 可靠性升级：从“能跑”到“能解释故障”

这次升级针对四篇 GPT-6 学习文档中的能力边界，完成了五项代码改造。本文只记录最终实现、必须成立的不变量、验证方式与仍然存在的边界。

## 1. 预约入口：请求事实 + CREATE Outbox

旧链路先写 Redis `PROCESSING`，然后在 HTTP 线程直接发 RocketMQ。若进程在两步之间退出，服务端没有可恢复的请求事实。

v4 增加 `tb_reservation_request`。`ReservationTransactionalService.acceptRequest` 在一个 MySQL 事务中同时写入：

1. `PROCESSING` 请求事实；
2. `CREATE_RESERVATION` 可靠任务。

HTTP 接口不再依赖 MQ 当时可用。Relay 在后台发布 CREATE，Broker 明确返回 `SEND_OK` 后才完成 Outbox 任务。消费者处理结果回写请求表，Redis 只是五分钟查询投影。请求状态使用单调 CAS，迟到的 CREATE 重投不能把 `PAID/CANCELLED/EXPIRED` 改回 `RESERVED`。

## 2. 订单超时：真实截止时间 + 复合 CAS

主动取消与超时关单已拆成两个入口。超时关单的 SQL 必须同时满足：

```sql
WHERE id = ?
  AND status = 1
  AND offer_expire_time <= NOW()
```

ORDER_TIMEOUT 任务的 `next_retry_time` 直接写入订单 `offer_expire_time`，不再将“15 分钟”偷藏在 RocketMQ delay level 对照表中。候补资格截止时间取 `min(当前时间 + offerMinutes, 活动结束时间)`。Docker 中显式设置 JVM 时区，保证 Java `LocalDateTime` 与 MySQL `NOW()` 处于同一时区。

## 3. 候补：严格 FIFO 与版本化 Resource Handoff

`SKIP LOCKED` 适合互相独立的后台任务，不适合对外承诺 FIFO 的业务队列。v4 在释放名额时使用阻塞的：

```sql
SELECT *
FROM tb_reservation_waitlist
WHERE activity_pass_id = ? AND status = 'WAITING'
ORDER BY request_id
LIMIT 1
FOR UPDATE;
```

候补入队和名额释放都先锁定 `tb_limited_pass_stock` 的活动行。因此同一活动的“队列是否为空”与“是否恢复公共库存”使用同一个串行化顺序。队首有异常有效订单或已过期时，事务会标记原因并继续选择下一人。

订单增加 `resource_version`。Redis claim 保存 `orderId:resourceVersion`，每次补位递增版本。`transfer-reservation.lua` 同时校验旧归属、旧版本和新用户现有归属，不匹配时拒绝覆盖。补偿 marker 不再七天过期，保证迟到重试也不会再次加库存。

## 4. 可靠任务：多实例租约、执行版本与 DEAD

任务状态为 `PENDING / RUNNING / DONE / DEAD`。每个应用实例以自己的 UUID 领取任务，使用 `FOR UPDATE SKIP LOCKED` 锁定互相独立的任务行，写入 `locked_by / lease_until / version`。外部副作用在短事务之外执行，完成或失败回写必须同时命中 owner 和 version。实例退出后，租约过期任务可被其他实例回收。

失败使用最长 300 秒的指数退避；达到 `max_retry` 后进入 DEAD。设置 `RELIABLE_TASK_ADMIN_TOKEN` 后，可通过 `POST /internal/reliable-tasks/{id}/replay` 明确重放死信。Actuator `/actuator/metrics` 可查看当前已到期积压数、最老到期任务等待时长、重试、死信和候补补位延迟；尚未到资格截止时间的定时关单不会被误算为积压。

## 5. 缓存：持久化失效意图、版本水位与多 JVM 广播

场馆更新在同一 MySQL 事务中递增 `cache_version` 并写入 `INVALIDATE_VENUE_CACHE` 任务，避免“提交后、afterCommit 回调前”宕机丢失失效事件。

执行失效时，Lua 更新 `cache:venue:version:{id}` 水位、删除主缓存与压测基线缓存，再向 `cache:venue:invalidate` 发布。所有应用实例订阅该频道并删除自己的 Caffeine 副本。异步重建将数据库行版本传给 `write-cache-if-version.lua`；旧查询的版本低于失效水位时，Redis 拒绝写入，Caffeine 也不会填充该旧值。Canal 仍然作为绕过应用写入的备用失效来源。

## 自动校验

```powershell
mvn clean test
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\smoke-test.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\reliability-test.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\cache-consistency-test.ps1
```

2026-09-09 在全新 Docker 数据卷上的实测结果：

- 100 个不同用户并发预约 10 份库存：10 笔有效订单、90 条 WAITING，MySQL/Redis 库存都为 0。
- 两笔订单同时释放：两个不同候补获得 OFFERED，公共库存仍为 0。
- 事务锁住真正队首时：释放请求阻塞，队尾不越过，库存不回池。
- Broker 停机时 HTTP 请求仍落库为 PROCESSING；Broker 恢复后自动到达 RESERVED。
- 支付/超时边界竞争只有一个终态获胜。
- 库存回补 Lua 同一任务执行两次返回 `1/0`，库存只增加一次。
- 两个应用 JVM 都预热旧 Caffeine 数据后更新场馆，两者都读到新值；低版本异步回写被 Lua 拒绝。

这些数据是功能与并发正确性验收，不是 QPS 压测，因此简历上可以写“100 用户并发校验无超卖”，不应由此推导生产吞吐量。

## 仍然存在的边界

- 系统追求至少一次投递 + 业务幂等，不声称外部副作用 exactly-once。
- Redis Pub/Sub 本身不持久化；持久化的是 MySQL 失效 Outbox。离线 JVM 重启后本地缓存为空，会重新经过 Redis 版本化读链路。
- 永久补偿 marker 用内存换取长时间幂等。生产环境应配合已归档活动的离线清理策略，不能任意设短 TTL。
- 支付接口是项目内状态演示，没有接入真实渠道的签名、回调和对账。
