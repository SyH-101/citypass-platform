## 表与升级顺序

修改 `tb_story`，新增 `status/version/publish_time/activity_pass_id/draft_expires_at/client_key` 等生命周期字段。新增四张表：

- `tb_story_attachment`：附件归属、状态、实际内容元数据、当前 attempt 与租约。
- `tb_story_attachment_ref`：当前引用和图片顺序。
- `tb_story_file_object`：每个 staging、候选 final、安全时间、删除确认、补扫时间与 `cleanup_task_id`。
- `tb_story_feed_progress`：事件已处理到的订阅记录 ID。

复用 `tb_reliable_task`，增加 `STORY_FEED` 与 `DELETE_STORY_FILE` 两类任务，不新建 MQ 或调度平台。

空 MySQL 卷由 Compose 依次导入基础初始化 SQL、Canal 用户和 v6。初始化 SQL 含重建基础表语句，只用于全新环境。已有库按尚未执行版本依次应用 v2 → v3 → v4 → v5 → v6；升级 v6 前停止全部旧应用实例，迁移后只启动新代码。不要对已有库重跑基础初始化 SQL。

历史 `tb_story` 回填 `PUBLISHED/version=1/publish_time=create_time`，原图片路径保持不变。[v6](../deploy/mysql/migration-v6-story-files.sql) 仅退休 `INDEX_ACTIVITY_SEARCH` 的 PENDING/RUNNING/DEAD，不更改预约、缓存待办。旧图片留在原卷，新上传走对象存储；旧按文件名上传与删除接口返回 410。

迁移脚本会拒绝已存在 v6 字段的重复 ALTER。DDL 可能部分提交，若失败需检查已完成步骤后继续；它不是可无限重跑的幂等迁移。最后新增的清理任务指针包含在 v6 内，已应用过中间开发版 v6 的环境应核对该字段；本次隔离环境已补齐。

Compose 项目为 `citypassfiles`，与原有开发项目分开。MySQL 8.0.36、Redis 7.2、RocketMQ 4.9.7、OpenResty、私有 MinIO 和 Java 8 应用均实际运行。验收网关/应用/MinIO 使用 18080/18081/19000 端口，上传/读取/宽限/补扫分别为 45/3/3/5 秒，便于观察到期和恢复。默认部署仍使用 300/120/120/3600 秒。

```powershell

docker compose -p citypassfiles up -d --build
```

## 本次发现并修正的问题

短周期墓碑补扫在存储故障时原本会重复建立未完成清理任务，挤占共享 Relay。对象现在持久保存当前清理任务 ID，持锁后检查旧任务状态，沿用 PENDING/RUNNING/DEAD，DONE 后才允许下一轮。修复后完整 17 项故障脚本通过，并增加同对象未完成任务唯一性检查。

精简 Java 8 镜像缺少系统 MIME 数据库，历史 PNG 的 `probeContentType` 会返回空。现在在已通过固定图片扩展名与实际目录边界后提供类型回退，保留 nosniff；新增实际读取、权限、穿越与符号链接测试验证该路径。
