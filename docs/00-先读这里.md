# 先读这里：用最短路径掌握 CityPass

不要从 Controller 一层层背代码。先抓住三个问题：

1. 请求如何从网关走到最终订单？
2. 用户取消后，一个名额如何安全地转给候补者？
3. Redis、MySQL、RocketMQ 任意一步失败时，系统靠什么收敛？

## 45 分钟第一遍

### 0～10 分钟：跑起来

```powershell
docker compose up -d --build
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\smoke-test.ps1
```

看到 `Success : True` 后再读代码。先有可观察结果，后面的状态机才不会变成抽象名词。

### 10～25 分钟：只读主链路

按顺序打开：

1. `ReservationController.reserve`：HTTP 入口。
2. `ReservationServiceImpl.reserve`：生成请求号、写 PROCESSING、发送 MQ。
3. `OrderMQConsumer`：CREATE/TIMEOUT 消息分流。
4. `ReservationServiceImpl.createOrderFromMQ`：时间窗、幂等、Lua 占位和候补决策。
5. `reservation-claim.lua`：库存、持有人、claim 为什么必须原子变化。
6. `ReservationTransactionalService.createOrder`：DB 条件扣减、订单和超时任务的事务边界。

这一遍只回答“正常预约如何成功”。

### 25～40 分钟：读补位链路

1. `ReservationServiceImpl.cancelOrder` 和 `cancelTimeoutOrder`。
2. `ReservationTransactionalService.releaseOrPromote`。
3. `ReservationWaitlistMapper.selectNextForUpdate`。
4. `transfer-reservation.lua` 与 `restore-stock.lua`。
5. `ReliableTaskScheduler`。

这一遍只回答“取消时为什么不一定加库存”。

### 40～45 分钟：复述五个不变量

- 一个用户对一个活动最多有一个有效订单或候补。
- DB 库存不小于 0。
- 补位时库存不变，名额归属变化。
- 支付和关单通过 CAS 竞争。
- MySQL 是最终账本，Redis 可以补偿或重建。

## 建议亲手做的五个实验

1. 库存设为 1，三位用户依次预约，观察 `RESERVED / WAITLISTED(1) / WAITLISTED(2)`。
2. 第一位用户取消，观察第二位变为 `source=WAITLIST`，第三位排位变为 1。
3. 候补补位用户支付后再次支付，观察第二次 CAS 失败。
4. 无候补用户取消，等待可靠任务把 DB 和 Redis 库存都恢复，再用同一用户重新预约。
5. 发布未来开始的活动，观察请求进入 `FAIL_NOT_STARTED`，Redis 库存不被占用。

## 学完后必须能回答

- 为什么请求号、订单号和候补补位订单号可以复用？
- 为什么候补顺序按 `request_id`，而不是候补表自增主键？
- 为什么自动补位事务中 DB 库存不能先加一再减一？
- 为什么唯一索引使用生成列 `active_user_id`？
- 为什么可靠任务与订单写在同一个本地事务里？
- 如果 Redis 全部丢失，哪些数据可以从 MySQL 恢复？
