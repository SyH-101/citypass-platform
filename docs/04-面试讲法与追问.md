# 面试讲法与追问

## 60 秒项目介绍

> CityPass 是我基于开源本地生活原型二次开发的城市活动发现与限量预约平台。我把原来通用的抢购场景重构成预约、候补和自动补位：入口用 OpenResty 令牌桶和用户滑动窗口限流，RocketMQ 做削峰，消费者用 Lua 原子维护 Redis 库存与名额归属，数据库再通过条件扣库存和有效订单唯一索引兜底。库存不足时用户可以进入 MySQL 持久化 FIFO 候补队列；取消或超时后，事务锁定队首并直接转移名额，候补为空才回补库存。跨 MySQL、Redis、MQ 的副作用通过本地可靠任务、幂等 Lua 和定时对账实现最终一致。我还把场馆、动态、订阅和评论统一到 CityPass 领域，并写了 Docker 全链路脚本验证关键状态转换。

## 三分钟展开顺序

1. **先讲业务矛盾**：热门活动需要削峰，未支付又会浪费稀缺容量。
2. **再讲不变量**：库存不为负、一人一个有效资格、补位不改库存、支付与关单互斥。
3. **讲正常链路**：MQ、时间窗、Lua、DB 事务。
4. **讲异常链路**：重复消息、DB 失败、Redis 补偿失败、延迟消息丢失。
5. **讲验证证据**：单元测试 + Docker 脚本，不编造 QPS。

## 高频追问

### 为什么不用 Redis List 直接做候补？

Redis List 快，但持久顺序、状态查询、唯一约束和事务更新都需要额外设计。这里选择 MySQL 作为最终队列，`request_id` 定义稳定顺序，`FOR UPDATE SKIP LOCKED` 让并发补位者不会选中同一人。Redis 只保留快速库存和名额归属。

### 为什么按 request_id，不按自增 id？

RocketMQ 是并发消费，先发送的消息不一定先插入候补表。入口请求号由 Redis 单调序列生成，更接近系统接受请求的顺序；候补表自增 id 只代表落库先后。

### 补位为什么不先 stock + 1 再 stock - 1？

同一个名额只是从旧用户转给新用户。中间若先加库存，其他请求可能抢走这个短暂出现的库存；两次写也扩大失败窗口。正确做法是订单所有权和候补状态转换，库存数量保持不变。

### Redis Lua 已经原子，为什么 DB 还要条件扣减？

Redis 可能重启、丢数据或发生补偿延迟。MySQL 是最终账本，`UPDATE ... SET stock=stock-1 WHERE stock>0 AND begin_time<=now AND end_time>now` 是最后防线。

### 为什么不做 Redis 和 MySQL 的分布式事务？

高并发预约更看重吞吐和可用性。项目用本地事务保证 DB 内一致，再用可靠任务、幂等补偿和对账收敛 Redis/MQ。代价是允许短暂不一致，必须能观察和重试。

### 支付和超时同时发生怎么办？

两者都以 `WHERE status=1` 做条件更新。数据库只允许一个更新成功：支付赢则状态为 2，关单赢则状态为 4。补位与回补只由成功关单的一方执行。

### 为什么取消后还能重新预约？

普通 `UNIQUE(user_id, pass_id)` 会永久阻止。表中使用生成列：只有状态 1、2、3、5 时 `active_user_id=user_id`，取消或退款后为 NULL。唯一索引只约束有效订单。

### 可靠任务会不会重复执行？

任务表的 `biz_key` 唯一，扫描器可重试。Redis 脚本还使用业务标记或 claim 所有权校验，因此重复执行不会重复加库存或重复转移名额。

## 不要说错

- 不要说 Redis 和 MySQL 强一致；这里是最终一致。
- 不要说实现了真实支付；这里只模拟订单状态 CAS。
- 不要说有数据库主从；当前没有配置主从数据源。
- 不要给出未实际压测的 QPS、TPS 或命中率。
- 不要把开源基础描述为自己从零完成。
