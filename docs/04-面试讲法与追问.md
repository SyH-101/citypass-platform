# 面试讲法与追问

## 90 秒项目介绍

> 我在黑马点评基础上重点改造了秒杀和缓存链路。秒杀入口有 OpenResty 总量令牌桶和 Redis 用户滑动窗口，提供两种写模式：A 模式在入口用 Lua 原子预扣，再通过 RocketMQ 事务消息异步建单；B 模式先入队，消费者再 claim，能把更多校验压力后移。最终落库时，我把 DB 条件扣库存、订单插入和超时关单任务放进一个本地事务，并用唯一索引保证一人一单。延迟消息、Redis 库存初始化和取消后的 Redis 回补都通过本地可靠任务重试，补偿 Lua 带 orderId 或幂等标记。支付和关单使用条件更新竞争终态，最后还有定时对账按订单表修正长尾差异。读取侧是 OpenResty、Caffeine、Redis、MySQL 四层链路，更新在事务提交后主动驱逐，并可用 Canal 处理绕过应用的数据库变更。

说完后停下，让面试官选择追问方向。

## 高频追问

### 为什么用了事务消息还要本地可靠任务？

事务消息保护的是“Redis 预扣结果与 CREATE 消息是否投递”。订单落库后还要发送 TIMEOUT 延迟消息，这是另一个 DB 到 MQ 的一致性窗口，所以用本地任务表与订单同事务提交。

### 为什么不直接上分布式事务？

秒杀链路更看重吞吐和可用性。这里把数据库订单表作为最终账本，通过幂等、重试、补偿和对账实现最终一致，代价是存在短暂不一致窗口。对于资金扣款会采用更严格的支付流水和回调设计。

### Redisson 锁已经保证一人一单，为什么还要唯一索引？

锁是运行时协调，会受租约、网络、配置和代码路径影响；唯一索引是数据库最终约束。Lua 降低热点、锁缩小竞争、唯一索引兜底，职责不同。

### 本地任务会不会重复执行？

会，设计目标就是至少一次。发送延迟消息可重复，因为关单是 CAS；Redis 回补脚本用 orderId marker；库存初始化脚本用 init marker，重复执行不会覆盖已扣减库存。

### 为什么逻辑过期还要物理 TTL？

逻辑过期用于热点平滑重建，但如果重建线程长期失败或对象被删除，没有物理 TTL 的旧值会永久占用并可能一直返回。更长的物理 TTL 是故障兜底。

### Canal 能保证强一致吗？

不能。binlog 解析、MQ 投递和消费都有延迟。应用写路径仍要在提交后主动删缓存，Canal 用来覆盖脚本改库、后台工具改库等旁路更新。

### 你做过压测吗？

没有真实数据就不要编数字。可以回答：已经把模式切换点、缓存命中标识和限流层次准备好，下一步用 JMeter/Gatling 分别测 A/B 的吞吐、P95/P99、Redis QPS、MQ 堆积和最终订单正确数，并先确定机器配置和数据规模。

## 简历写法

项目名可以写：**黑马点评 Pro｜高并发秒杀与多级缓存系统**。

- 设计 A/B 两种异步秒杀链路，使用 Redis Lua、RocketMQ 事务/普通消息、Redisson 与数据库唯一索引处理削峰、库存预扣和一人一单。
- 将库存扣减、订单落库与超时任务纳入本地事务，并以可靠任务、幂等补偿 Lua、延迟关单和定时对账处理跨组件最终一致性。
- 构建 OpenResty、Caffeine、Redis、MySQL 多级缓存，修复缓存锁所有权与提交前驱逐问题，并通过 Canal 覆盖旁路更新。
- 实现网关令牌桶与用户滑动窗口限流，补齐订单越权校验、一次性验证码和上传目录穿越防护。
