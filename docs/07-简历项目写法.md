# CityPass 的三条简历描述

项目名可以使用 **CityPass｜城市活动预约与内容分享平台**。简历只放三点，每一点对应一篇学习文档，面试时从业务问题讲到关键代码和失败边界。

- 设计限量预约与候补补位流程，通过请求事实与 Outbox 可靠受理、RocketMQ 异步执行、Redis Lua 预占及 MySQL 条件扣减防止超卖；以订单条件迁移处理支付与超时竞争，锁定已入队候补队首并用资源版本完成名额交接。
- 构建 OpenResty、Caffeine、Redis 多级读取，使用逻辑过期与互斥重建控制回源；场馆更新同事务保存版本与失效待办，借助 Redis 与网关版本水位拒绝旧数据回填，并对 Redis 故障时的数据库降级流量设置并发上限。
- 实现笔记草稿、版本编辑与软删除，以及私有图片直传、独立 final 封存和真实内容检查；通过持久尝试记录、延迟清理与墓碑补扫处理文件残留，发布同事务登记 Feed 事件，按版本和批次进度恢复信息流传播。

三条较长时，优先保留“做了什么、解决哪个问题、最重要的约束”。不要为了缩短篇幅改成一串中间件名词，也不要添加没有实际压测证明的 QPS 或延迟收益。

## 怎样介绍自己的贡献

我保留了开源原型的通用登录与内容能力，主要改造了预约资源交接、缓存一致性和笔记文件生命周期。预约重点解释一个名额从直接预约者到候补者的过程；缓存重点解释一个旧查询如何晚于更新返回；文件重点解释复制成功但数据库提交失败后如何收尾。

具体声明应以你能讲清楚、能现场定位的代码为准。学习文档中的参考回答供准备使用，不能替代个人经历，也不能把基于开源项目的改造说成全部从零原创。

## 哪些表述有证据

| 可复述的结果 | 实测依据 | 应当保留的边界 |
| --- | --- | --- |
| 百人竞争得到 10 个有效名额、90 个候补 | 真实 MySQL、Redis、MQ 可靠性脚本 | 正确性实验，没有测生产容量 |
| 已持久化候补按请求号选择，不跳过锁住的合法队首 | 队首锁与并发晋升实验 | MQ 消费乱序时不保证全局 HTTP 到达顺序 |
| Broker 恢复后继续处理已受理请求 | 停机与恢复实验 | 仍允许重复投递，需要消费幂等 |
| 双 JVM 读取新值，旧版本回填被拒绝 | 缓存与网关脚本 | 允许在途旧读，Pub/Sub 不保证离线消息补发 |
| 私有 MinIO 真实直传、发布、访问和清理通过 | 文件脚本与浏览器截图 | 云端 OSS 联调、内容审核和生产压测未完成 |

当前支付只模拟本地订单状态，没有真实渠道扣款、退款或资金对账。当前缓存与 Feed 都有明确的异步可见延迟，不应写成跨系统强一致；执行器租约也不保证外部调用绝不重复。
