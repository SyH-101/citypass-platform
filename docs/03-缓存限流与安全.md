# 缓存、限流与安全

## 多级缓存读取

```text
OpenResty shared dict → Caffeine → Redis 逻辑过期值 → MySQL
```

OpenResty 缓存完整响应，Caffeine 减少 Redis 网络访问，Redis 逻辑过期允许热点请求先返回旧值并由一个线程异步重建。Redis 值同时设置更长的物理 TTL，防止长期故障留下永久脏数据。

## 缓存互斥锁的正确释放

锁值使用随机 token。释放时执行 Lua：只有 Redis 中的值仍等于自己的 token 才删除。这样线程暂停超过锁 TTL 后，不会误删后来线程的新锁。

未获取锁的请求采用有上限的短暂重试，避免递归调用造成栈增长。获取锁后再查一次 Redis，防止前一个线程刚完成重建却重复查库。

## 更新后的驱逐时机

店铺更新处于数据库事务内。如果先删缓存再提交，另一个请求可能在提交前读到旧 DB 值并重新写入缓存。`ShopCacheInvalidator.evictAfterCommit` 在事务提交成功后才驱逐：

1. Caffeine。
2. Redis。
3. 可选 OpenResty 内部 purge 接口。

Canal 用于兜住绕过应用的数据库更新。它不是更新接口正确性的替代品。

## 两层限流

- OpenResty 令牌桶限制秒杀入口总 QPS，保护 Tomcat 和 Redis。
- Redis ZSet 滑动窗口按 userId 限速，限制单用户刷接口。

滑动窗口脚本使用 Redis `TIME`，避免多台应用服务器时钟偏差。限流只匹配 `POST /voucher-order/seckill/{id}`，结果轮询不会消耗下单额度。

令牌桶中 `last` 的推进量必须是 `refill / rate * 1000` 毫秒。原代码把令牌数直接乘 1000，在 rate 不为 1 时会把时间推到未来，导致长时间无法补充令牌。

## 已修的安全边界

- 支付 SQL 同时匹配 `orderId + currentUserId + unpaid`。
- 排队结果写入 owner key，结果 key 过期后再用订单表 userId 校验。
- 登录成功删除验证码；登出删除 token。
- 商铺/优惠券写接口和上传接口要求登录，公开 GET 仍可匿名访问。
- 上传只接受图片后缀和 `image/*` 类型，限制为 5 MB。
- 删除图片改用 DELETE，并通过规范化路径保证目标位于配置的上传根目录。

后台管理尚未区分普通用户和管理员，简历或面试中应明确说“完成登录鉴权，RBAC 是下一阶段边界”。
