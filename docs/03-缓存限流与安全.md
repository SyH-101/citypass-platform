# 缓存、限流与安全边界

## 多级缓存为什么存在

场馆详情读多写少，适合多级缓存：

| 层级 | 位置 | 优势 | 一致性代价 |
|---|---|---|---|
| L1 | OpenResty shared dict | 请求不进入 JVM | 使用本实例版本水位与显式驱逐 |
| L2 | Caffeine | 纳秒级本地读取 | 多实例各有副本 |
| L3 | Redis | 多实例共享 | 网络往返 |
| L4 | MySQL | 最终数据 | 容量最贵 |

`MultiLevelCacheService` 使用空值缓存防穿透、互斥重建防击穿，并给 TTL 增加抖动防止大量 Key 同时失效。

## 为什么事务提交后再删缓存

如果数据库事务尚未提交就删缓存，另一个请求可能在提交前读到旧 DB 数据并重新写入缓存。当前写路径把 Venue 更新、cacheVersion 递增与失效任务放在同一 MySQL 事务；任务提交后推进 Redis 与 OpenResty 的版本水位，清理 Caffeine/Redis，并逐一驱逐配置的网关地址。

Java 只对成功的公共详情响应发送版本和内部可缓存标记。OpenResty 将版本与正文作为一个缓存项，在回填和 purge 时使用同一场馆短锁，并拒绝低于水位的迟到响应。它仍是异步最终一致方案：任务执行前存在短窗口，进入 DEAD 后需要运维处理；Canal 用于覆盖绕过应用的 SQL 更新。

## 两级限流各自保护什么

1. OpenResty 令牌桶按系统总量限制预约入口，先保护 Tomcat 和 Redis。
2. Java 滑动窗口按登录用户限制请求，防止单用户持续刷接口。

滑动窗口脚本使用 Redis `TIME`，避免多台机器的本地时钟不一致。查询预约结果、支付和取消不占用创建预约的限流额度。

## 登录与所有权

- 登录验证码只使用一次，成功后立即删除。
- Token 存在 Redis Hash 中，刷新拦截器滑动续期。
- 公共读取仅开放场馆、通行证、部分动态和评论列表。
- 发布、订阅、评论、预约、支付、取消均需登录。
- 查询预约、支付、取消和删除评论都校验资源所有者。
- 上传文件使用服务端生成路径，并阻止 `../` 路径穿越。

## 当前安全边界

CityPass 是面试用后端工程，不应声称具备完整商业安全体系。管理写接口目前只要求登录，尚未加入组织者角色、OAuth2、支付签名、短信供应商、内容审核和审计后台。简历中可以写“完成登录和资源所有权校验”，不要写“企业级权限系统”。
